## P1. Бары зависели от стакана — FIXED
- **Что**: для исследования сезонности по 16 активам за полгода нужны только сделки (≈18 МБ/день на все активы).
  Стакан стоил бы ≈ 1–4 ГБ/день на актив, то есть сотни ГБ. Но `derive` строил бары только из `events/`,
  а `events/` собирается только при наличии стакана.
- **Почему**: производные датасеты проектировались как «следующий слой после событий» (L1 тоже нужен стакан).
- **Решение**: `src/derived/trade_bars.py` — для UTC-дней без событий, но с покрытием сделок (файлы D и D+1: OKX режет
  сделки по UTC+8) стадия `derive` строит `bars_1s`/`bars_1m` напрямую из нормализованных сделок. `mid_close`/`spread_close`
  в таких барах пустые. День с событиями всегда имеет приоритет. Ключ манифеста `derive_trades:<день>`.
- **Проверено**: BTC-USDT, 181 UTC-день, 100% минут со сделками.
- **Урок**: «производные данные» должны объявлять, какие входы им реально нужны, и строиться из минимально достаточных.

## P2. Движок принимает только L2 — FIXED (адаптер) + NOTE
- **Что**: `BacktestEngine.run_batches` ждет события EVENT_SCHEMA со стаканом. Для часовых стратегий на барах движок был
  бы недоступен, и пришлось бы писать второй, «упрощенный» бэктестер на каждую идею — ровно то, чего мы хотели избежать.
- **Решение**: `src/backtest/bar_feed.py::bars_to_events` — из минутных баров строит синтетический стакан
  (bid/ask = close ∓ полуспред, бесконечный объем) на закрытии каждой минуты. Движок, Portfolio, комиссии, задержки — те же.
- **Проверено**: движок и независимая векторная оценка расходятся ≤ 0.1% по PnL и дают одинаковое число сделок.
- **NOTE (ограничения)**: нет глубины и проскальзывания от размера; спред задан параметром; внутрибарных движений нет;
  модель очереди для пассивных ордеров здесь бессмысленна. Подходит для малых размеров на ликвидных активах.

## P3. Погода и точка во времени — FIXED
- **Что**: в проекте не было внешних данных. Главный риск — подсмотреть в будущее: суточная температура за день D известна
  только после его конца.
- **Решение**: `src/external/weather.py` (Open-Meteo Archive, кэш в `data/external/weather`). `load_daily(lag_days=1)` по умолчанию
  сдвигает ряд: в строке D лежит наблюдение за D-1. Признаки (z-аномалия) считаются по скользящему окну, сдвинутому на 1.
- **NOTE**: источник — реанализ ERA5, а не прогноз, который был доступен в тот момент. Для поиска закономерности допустимо,
  для оценки реальной торговой пригодности — нет (нужны архивные прогнозы).

## P4. Нет параметров инструмента — FIXED
- **Что**: движку нужны шаг цены и лот; в проекте они задавались вручную флагами (`--tick`, `--lot`).
- **Решение**: `OkxFetcher.instrument_specs()` (tickSz, lotSz, minSz) из публичного `/public/instruments`.

## P5. Спред по Corwin–Schultz — FIXED + NOTE
- **Что**: первая версия оценивала полуспред по часовым high/low (Corwin–Schultz). Для BTC получилось **9.8 б.п.**
  Реальный спред из нашего же L1 (2024-01-01): **медиана 0.023 б.п.** (1 тик). Издержки стратегии были бы раздуты на порядки.
- **Почему**: оценка по high/low предполагает, что диапазон часа — это спред + дисперсия; в крипте волатильность
  доминирует, и оценка уходит в сторону.
- **Как поймали**: сверкой с реальными данными на единственном активе, где они есть (BTC, 2 дня L1).
  Без этой сверки результат выглядел бы правдоподобно.
- **Решение**: `OkxFetcher.spread_snapshot()` — текущий спред по всем инструментам одним запросом; полуспред =
  max(половина спреда, половина тика). Проверено: прокси 0.016 б.п. против реальных 0.023 б.п. для BTC.
- **NOTE**: это снимок 2026 года, а не история 2024. Для ранжирования активов по ликвидности годится, для абсолютных
  издержек — приблизительно. Точный путь — L1 из стакана, но он требует сотен ГБ.

## P6. Тесты пишут в боевой каталог логов — OPEN
- **Что**: в `logs/pipeline-*.log` попадают записи от pytest (`/private/var/.../pytest-of-kyle/...`, «Ночной запуск упал»).
  Журнал перемешан с реальными запусками, вкладка «Логи» показывает ложные ERROR.
- **Почему**: `setup_logging` берет `PIPELINE_LOG_DIR` из окружения при импорте, а тесты его не переопределяют.
- **Решение**: в `tests/conftest.py` — autouse-фикстура, подменяющая `PIPELINE_LOG_DIR` на tmp. Это зона QA → записано в ISSUES.md.

## P7/P8. «Только сделки»: молчаливые no-op и отсутствие проверок качества — FIXED
- **Что**: `--stage all` на данных без стакана отработал без ошибок и предупреждений, но `validate` и `derive` ничего
  не сделали (0 дней). Худший вид сбоя: данные кажутся обработанными, а проверок на самом деле не было.
- **Решение**: derive — см. P1. Для validate — `src/validation/trades.py`: дубли trade_id, цена/объем <= 0, паузы между сделками,
  скачки цены с возвратом, покрытие минут суток. Пропущенные дни ищутся и по дням только со сделками.
- **Проверено**: BTC-USDT 181 день: 179 OK / 2 WARN. Оба WARN — события, а не ошибки данных (день начинается с апдейтов;
  3 января 2024 — реальный обвал рынка: 20 скачков с возвратом за секунду).
- **Урок**: каждый «режим данных» должен иметь свой набор проверок; иначе «зеленый» отчет означает лишь «ничего не проверялось».

## P9. Jupyter — FIXED
- **Что**: в первой же запущенной копии шаблона ячейка с `asyncio.run(fetcher.instrument_specs(...))` упала:
  `RuntimeError: asyncio.run() cannot be called from a running event loop`. Утилиты проекта асинхронные, а ноутбуки уже
  работают внутри цикла событий.
- **Как поймали**: шаблон был исполнен целиком (nbclient), а не просто написан.
- **Решение**: `src/utils/sync.py::run_sync` (в работающем цикле запускает корутину в отдельном потоке) и синхронные
  обертки `src/research/market.py`.

## P10. Циклический импорт — FIXED
- **Что**: `validation.runner` стал импортировать `derived.trade_bars`, а `derived.runner` импортировал `events_files` из `validation.runner`.
- **Решение**: `events_files` вынесена в нейтральный `src/storage/layout.py`.
- **Урок**: общие функции раскладки каталогов — отдельный слой ниже validation/derived/api.

## P11. Округление к тику — FIXED
- **Что**: сверка «движок против независимой векторной оценки» показала расхождение до 214 USDT (10% комиссий) на XRP при ~1 USDT на BTC.
- **Причина**: расхождение на сделку ≈ −0.5 тика (корреляция 0.96 по активам). Движок округляет bid вниз и ask вверх к сетке цены,
  как биржа; векторная оценка тик игнорировала. У активов с крупным тиком (BCH, ADA, XRP — 2 б.п.) это заметно, у BTC (0.02 б.п.) нет.
- **Решение**: в издержки векторной оценки добавлено +0.5 тика на сторону. Остаток ≲ 5% комиссий (постоянное количество в движке против
  постоянной суммы в оценке). Эталон — движок.
- **Урок**: две независимые оценки одной величины — самый дешевый способ найти упрощение; расхождение надо объяснять, а не округлять.

## P12. Тест сезонности: слепой, затем миражный — FIXED
Самый поучительный пункт. Три итерации, каждая поймана калибровкой на синтетике с известной истиной:
1. **Циклический сдвиг сигнала на случайное число суток** (плацебо). На случайных блужданиях 0 из 300 отвержений (ожидалось ~15),
   на ряде с эффектом 15 б.п. в 4 часах — мощность 0%. **Причина**: при сдвиге «за конец» ряда сигнал оказывался построен по
   данным ПОСЛЕ доходности, которую умножает (его 28-дневное окно захватывало ее саму) → ложно большие значения в плацебо,
   разброс нулевого распределения втрое выше реального. «Ничего не найдено» означало бы лишь «тест ничего не видит».
2. **Ограничение допустимых сдвигов окном признака**. Ложные срабатывания 8%, мощность 14% при 15 б.п. Лучше, но слабо.
3. **Центрирование плацебо** (учет дрейфа) → ложные срабатывания выросли до **15%** при номинальных 5%. Откатил: сдвиг сигнала не
   обменяем, поэтому «поправки» к нему только прячут проблему.
- **Решение**: `stats.edge_ttest` — t-тест суточных сумм `S·(r − r̄)`: при сигнале только из прошлого вклад часа — разность
  мартингала с нулевым средним, вычитание среднего убирает ложный edge от дрейфа, единица независимости — сутки. Калибровка:
  ложные срабатывания 4.6–5.3% (случайное блуждание, ± дрейф, ± кластеры волатильности), мощность 60% при 15 б.п. и 100% при 30 б.п.
- **Влияние на выводы**: после шага 2 один актив (TRX) выглядел «значимым» (q = 0.03). С корректным тестом он — t = 1.7, q = 0.44;
  разбор показал, что весь его эффект в январе–феврале (t = 0 в апреле–июне).
- **Артефакты**: `calibrate.py` → `results/calibration.json` (воспроизводимо). Тест селективности откалиброван тем же способом
  (ложные 3.7–5.2%, мощность 80% при +10 б.п.).
- **Урок**: статистический тест — такой же код, как и стратегия, и тоже требует проверки на данных с известным ответом ДО чтения
  результатов. Особенно когда результат «ничего нет»: он выглядит безопасно и именно поэтому его не проверяют.

## P13. Мощность дизайна — NOTE
- Реальная часовая волатильность BTC ≈ 56 б.п.; при окне 28 суток и 6 месяцах данных дизайн обнаруживает эффект ≥ ~15 б.п. в 4 часах
  (60%) и ≥ 30 б.п. (100%). Эффекты меньше — не увидит. Это граница вывода «не найдено»: **отрицательный результат относится
  к эффектам не меньше этого размера**. Для taker 10 б.п. (≈ 20 б.п. на круг) торгуемы только эффекты крупнее.

## P14. Погода — NOTE
- Реанализ ERA5, а не прогноз, который был доступен (PIT-лаг 1 день снимает прямое заглядывание, но не разницу «известно/оценено»).
- Без FDR-поправки на данных были бы «находки»: BTC (сырой p ≈ 0.02, +9.8 б.п.) и XRP (p ≈ 0.05, −11.9 б.п., противоположный знак).
  После поправки на 16 активов q ≈ 0.3–0.4. Из 48 тестов сырых p < 0.05 — 4 при ожидаемых ~2.4 случайно.

## Что подтвердилось про механику (ответ на цель №1)
Конвейер «гипотеза → данные → проверка качества → признаки → движок → статистика → решение» проходится целиком на инструментах проекта
без самописных бэктестеров. Самое ценное, что дал эксперимент, — не результат по активам, а найденные дефекты инструментов:
слепой статистический тест (P12), завышенные издержки (P5), игнорирование тика (P11), отсутствие проверок качества для «только сделок»
(P8), несовместимость с Jupyter (P9). Все исправлены в проекте и вынесены в `src/research/`, `src/validation/`, `src/derived/`.
