# Контроль качества данных (Data Quality Stage)

## 1. Назначение и архитектура

Этап валидации данных (`stage="validate"`) выполняет потоковую проверку нормализованных событий (`events/*.parquet`) для каждого инструмента и торгового дня.

Цель этапа — гарантировать физическую и логическую корректность рыночных данных перед запуском бэктеста и симуляции стратегий, а также локализовать дефекты рыночных фидов биржи OKX.

Валидация выполняется в один потоковый проход (`pq.ParquetFile.iter_batches`), используя легковесную реализацию стакана (`_Book` в [src/validation/day.py](file:///Users/kyle/main/py_files/backtest_strat/src/validation/day.py)). Это обеспечивает высокую скорость работы и независимость от параметров инструмента (шага цены и лота).

---

## 2. Список проверок

| Имя проверки | Описание | Порог по умолчанию | Статус при нарушении |
|---|---|---|---|
| `crossed_book` | Лучший bid $\ge$ лучшего ask после применения сообщения | $> 0$ случаев | `FAIL` |
| `book_gap` | Пауза между сообщениями стакана | $> 30\,\text{с}$ $\to$ `WARN`<br>$> 300\,\text{с}$ $\to$ `FAIL` | `WARN` / `FAIL` |
| `no_initial_book` | Структура начала суток и доступность первичного снапшота | Снапшот $\le 60\,\text{с}$ $\to$ `OK`<br>Апдейты, снапшот $\le 120\,\text{с}$ $\to$ `WARN`<br>Снапшота нет вовсе $\to$ `FAIL` | `WARN` / `FAIL` |
| `trade_vs_book` | Доля сделок вне спреда (покупка ниже bid или продажа выше ask) | $> 1\%$ от общего числа сделок | `WARN` |
| `price_spike` | Кратковременный скачок mid-цены | Скачок $> 50$ б.п. за 1–2 с с откатом $\ge 80\%$ за 5 с | `WARN` |
| `non_positive` | Некорректные значения цен и объемов | Цена или объем сделки $\le 0$, объем уровня стакана $< 0$ | `FAIL` |
| `snapshot_drift` | Расхождение восстановленной книги со снапшотами биржи | Несовпадение лучшей цены $> 5\%$ | `WARN` |
| `no_events` | Файл событий пуст (0 записей) | Файл не содержит строк | `FAIL` |
| `validator_error` | Исключение при чтении или парсинге файла | Любая непредвиденная ошибка | `FAIL` |

### Проверки по одним сделкам (Trades-Only Validation)

Для дней, где стакан отсутствует или исследование строится только на сделках (`src/validation/trades.py`), запускается специализированный набор проверок:

| Имя проверки | Описание | Порог по умолчанию | Статус |
|---|---|---|---|
| `no_trades` | Наличие сделок за сутки | 0 сделок | `FAIL` |
| `duplicate_trade_ids` | Уникальность биржевых идентификаторов | Любые дубликаты `trade_id` | `FAIL` |
| `non_positive` | Корректность цен и объемов сделок | Цена $\le 0$ или объем $\le 0$ | `FAIL` |
| `trade_gaps` | Паузы в потоке сделок (включая края суток UTC) | Пауза $> 1\,\text{ч}$ $\to$ `WARN`<br>Пауза $> 6\,\text{ч}$ $\to$ `FAIL` | `WARN` / `FAIL` |
| `trade_price_spike` | Спайк цены за минуту с откатом | Скачок цены $\ge 5\%$ с возвратом $\ge 80\%$ за минуту | `WARN` |
| `low_coverage` | Доля активных минут со сделками | Доля минут $< 25\%$ | `WARN` |

## 3. Статусы и действия оператора

Каждый день получает статус, равный наихудшему статусу входящих в него проверок (`FAIL` > `WARN` > `OK`):

### 🟢 `OK`
- **Значение:** Данные чистые, книга непрерывна, сделки согласованы со стаканом.
- **Действие:** День полностью готов для бэктеста и обучения моделей.

### 🟡 `WARN`
- **Значение:** Обнаружены некритичные аномалии. Например:
  - День начался с дифференциальных апдейтов, а первый снапшот пришел через 20–100 секунд (характерно для некоторых дней OKX, таких как `2024-01-02`).
  - Небольшие паузы в стакане ($30\,\text{с} < \text{gap} \le 300\,\text{с}$).
  - Небольшая доля сделок вне спреда (может возникать из-за сетевой задержки доставки тиков биржи).
  - Кратковременные спайки с возвратом цены.
- **Действие:** Бэктест запускать можно. Движок симуляции ([BacktestEngine](file:///Users/kyle/main/py_files/backtest_strat/src/backtest/engine.py)) автоматически дождется первого снапшота перед вызовом `on_start` и проигнорирует сделки до этого момента. Однако следует учитывать, что в периоды гэпов активность рынка отсутствовала.

### 🔴 `FAIL`
- **Значение:** Критические дефекты, делающие симуляцию недостоверной:
  - Перевернутый стакан (`best_bid >= best_ask`).
  - Отрицательные цены или объемы.
  - Полное отсутствие снапшотов за день (книгу восстановить невозможно).
  - Гэп в стакане $> 300\,\text{с}$ (5 минут).
  - Пустой или поврежденный parquet-файл.
- **Действие:** Бэктест на таком дне проводить нельзя (симуляция даст неверные PnL или выбросит исключение). Рекомендуется:
  1. Проверить сырые архивы за данный день в `data/raw/`.
  2. Перезапустить нормализацию с флагом `--force`.
  3. Если дефект присутствует в сырых данных биржи — исключить день из тренировочной/тестовой выборки.

## 4. Конфигурация порогов (`Thresholds`)

Пороги проверок инкапсулированы в датаклассе [Thresholds](file:///Users/kyle/main/py_files/backtest_strat/src/validation/day.py):

```python
@dataclass(frozen=True)
class Thresholds:
    gap_warn_s: float = 30.0              # Порог предупреждения о паузе стакана (сек)
    gap_fail_s: float = 300.0             # Порог фатальной паузы стакана (сек)
    initial_book_max_s: float = 60.0      # Макс. задержка первого снапшота от 00:00 UTC (сек)
    first_snapshot_warn_s: float = 120.0  # Макс. задержка первого снапшота при старте с апдейтов (сек)
    trade_outside_warn: float = 0.01      # Доля сделок вне спреда (1%)
    spike_bps: float = 50.0               # Скачок mid-цены в базисных пунктах
    spike_reversal: float = 0.8           # Доля отката спайка (80%)
    spike_reversal_window_s: int = 5      # Окно поиска отката (сек)
    snapshot_best_price_warn: float = 0.05# Порог расхождения со снапшотами (5%)
    max_examples: int = 5                 # Макс. число примеров аномалий в отчете
```

При программном вызове экземпляр `Thresholds` можно передавать в [validate_symbol](file:///Users/kyle/main/py_files/backtest_strat/src/validation/runner.py) или [validate_events_file](file:///Users/kyle/main/py_files/backtest_strat/src/validation/day.py).

## 5. Формат отчета и кэширование

Результаты валидации каждого дня сохраняются в формате JSON:
`data/processed/<exchange>/<symbol>/validation/<YYYY-MM-DD>.json`.

### Структура сохраненного файла:
```json
{
 "fingerprint": {
  "name": "2024-01-01.parquet",
  "size": 1234567,
  "version": 1
 },
 "report": {
  "day": "2024-01-01",
  "status": "OK",
  "events": 2500000,
  "book_messages": 1800000,
  "trades": 700000,
  "snapshots": 1440,
  "first_ts": "2024-01-01T00:00:00.018Z",
  "last_ts": "2024-01-01T23:59:59.980Z",
  "checks": [
   {
    "name": "crossed_book",
    "status": "OK",
    "detail": "Перевернутой книги нет",
    "value": 0.0,
    "examples": []
   }
  ],
  "stats": {
   "max_gap_s": 4.2,
   "trades_outside_share": 0.0002,
   "snapshot_best_price_mismatch": 0.0,
   "snapshot_best_qty_mismatch": 0.11,
   "spikes": 0.0,
   "crossed": 0.0
  }
 }
}
```

### Механизм кэширования:
1. Валидация **идемпотентна**. При повторном запуске, если размер файла и `REPORT_VERSION` не изменились, отчет считывается из кэша (`from_cache=True`), что занимает доли миллисекунды.
2. При изменении размера `.parquet` файла или при передаче флага `force=True` отчет рассчитывается заново.
3. При изменении алгоритмов проверки константа `REPORT_VERSION` инкрементируется, что приводит к автоматическому пересчету всех отчетов.
4. Запись отчетов атомарна (через временный файл `*.json.tmp` с последующим `os.replace`) и защищена межпроцессным файловым замком `.lock`.

## 6. Пропущенные дни (`missing_days`)

Раннер валидации отслеживает непрерывность торговых дней в собранном диапазоне:
- Границы диапазона определяются минимальной и максимальной датой имеющихся файлов событий `[min_day, max_day]`, с учетом фильтров `start` и `end`.
- Если между крайними датами диапазона отсутствует хотя бы один календарный день, он заносится в список `missing_days`.
- При наличии любого `missing_days` общий статус символа `ValidationSummary.status` становится `FAIL`.

В API и Web UI список пропущенных дней подсвечивается отдельной метрикой и предупреждением:
`"Нет событий за дни внутри собранного диапазона: 2024-01-02"`.

## 7. Запуск валидации

### 1. Через CLI (`src.cli`)

Только валидация существующих данных:
```bash
python -m src.cli --exchange okx --symbol BTC-USDT --stage validate --start 2024-01-01 --end 2024-01-10
```

Полный пайплайн (скачивание $\to$ нормализация $\to$ валидация $\to$ производные):
```bash
python -m src.cli --exchange okx --symbol BTC-USDT --stage all --mode backfill --start 2024-01-01 --end 2024-01-10
```

Принудительный пересчет отчетов:
```bash
python -m src.cli --exchange okx --symbol BTC-USDT --stage validate --force
```

### 2. Через Web UI

1. Откройте вкладку **«Качество данных»** в дашборде.
2. Введите тикер (например, `BTC-USDT`).
3. На экране отобразятся счетчики `🟢 OK`, `🟡 WARN`, `🔴 FAIL`, число пропущенных дней, а также разворачиваемые карточки по каждому дню со списком проверок и примерами проблемных сообщений.
4. Для пересчета запустите задачу со стадией **«Только проверить»** на вкладке «Запуск пайплайна».

### 3. Через REST API

```http
GET /validation/okx/BTC-USDT
```
Возвращает:
```json
{
  "days": [ ... ],
  "missing_days": [ "2024-01-02" ],
  "not_validated": [ "2024-01-03" ]
}
```
