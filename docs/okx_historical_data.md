# Спецификация исторических данных OKX (OKX Historical Market Data)

В данном документе собрана техническая спецификация по сбору, форматам, эндпоинтам и подводным камням выгрузки исторических рыночных данных (**Trades** и глубокий **L2 Order Book**) с биржи **OKX**.

Документ предназначен для последующей реализации модулей Ingestion (`OkxFetcher`) и Normalization (`OkxNormalizer`).

---

## 1. Общая архитектура и источники данных

Для получения исторических данных OKX используются три уровня доступа:

1. **Прямые CDN-архивы (Основной источник для Backfill и Daily):**
   * Данные хостятся на статических распределенных серверах OKX (`static.okx.com`, кэшируемых через Cloudflare и AWS CloudFront).
   * **Аутентификация:** **НЕ ТРЕБУЕТСЯ** (полностью публичный анонимный доступ по протоколу HTTP/2 и HTTP/1.1).
   * **Скорость и лимиты:** Практически без ограничений по пропускной способности; файлы скачиваются потоково на максимальной скорости сети.
2. **Публичный Резолвер Ссылок (`priapi`):**
   * Внутренний JSON RPC бэкенд веб-интерфейса `https://www.okx.com/historical-data`.
   * Позволяет программно запросить список актуальных CDN-ссылок по инструменту и диапазону дат.
   * **Аутентификация:** **НЕ ТРЕБУЕТСЯ**.
3. **Публичный REST API v5 (`api/v5/market/...`):**
   * Используется для получения свежей истории сделок за последние 3 месяца или текущего снимка книги заявок.
   * **Аутентификация:** **НЕ ТРЕБУЕТСЯ** для публичных рыночных каналов.

## 2. Эндпоинты, URL и параметры запросов

### 2.1. Прямые CDN-ссылки (Direct CDN Downloads)

#### А. Исторические сделки (Trades)
* **Шаблон URL:**
  ```text
  https://static.okx.com/cdn/okex/traderecords/trades/daily/{YYYYMMDD}/{instId}-trades-{YYYY-MM-DD}.zip
  ```
* **Примеры:**
  * Spot: `https://static.okx.com/cdn/okex/traderecords/trades/daily/20240101/BTC-USDT-trades-2024-01-01.zip`
  * Swap (Perpetual): `https://static.okx.com/cdn/okex/traderecords/trades/daily/20240101/BTC-USDT-SWAP-trades-2024-01-01.zip`
* **Формат архива:** `.zip` архив, содержащий ровно один `.csv` файл.
* **Размер файла:** ~1.5–3 МБ в сжатом виде за 1 день по активным парам (BTC, ETH).

#### Б. Глубокий стакан L2 (Order Book 400 уровней)
* **Шаблоны URL:**
  * **Актуальный путь (2025–2026):**
    ```text
    https://static.okx.com/cdn/okx/match/orderbook/pro/L2/400lv/daily/{YYYYMMDD}/{instId}-L2orderbook-400lv-{YYYY-MM-DD}.tar.gz
    ```
  * **Архивный путь (2023–2024):**
    ```text
    https://static.okx.com/cdn/okx/match/orderbook/L2/400lv/daily/{YYYYMMDD}/{instId}-L2orderbook-400lv-{YYYY-MM-DD}.tar.gz
    ```
* **Примеры:**
  * Spot: `https://static.okx.com/cdn/okx/match/orderbook/pro/L2/400lv/daily/20261008/BTC-USDT-L2orderbook-400lv-2026-10-08.tar.gz`
  * Swap: `https://static.okx.com/cdn/okx/match/orderbook/pro/L2/400lv/daily/20261008/BTC-USDT-SWAP-L2orderbook-400lv-2026-10-08.tar.gz`
* **Формат архива:** `.tar.gz` архив, содержащий один файл данных `.data`.
* **Размер файла:** ~120–150 МБ в сжатом виде (tar.gz), около **1 ГБ** в распакованном виде за 1 день для SPOT. Для SWAP — ~350 МБ в архиве, до **3–4 ГБ** в распакованном виде.

### 2.2. Публичный Резолвер Ссылок Архивов (Resolver API)

Если прямой URL не найден (например, для специфичных дат или инструментов), можно запросить актуальные ссылки через резолвер:

* **Метод:** `POST`
* **URL:** `https://www.okx.com/priapi/v5/broker/public/trade-data/download-link`
* **Headers:** `Content-Type: application/json`, `User-Agent: Mozilla/5.0 ...`
* **Тело запроса (Request Body):**
  ```json
  {
    "module": "1",
    "instType": "SPOT",
    "instQueryParam": {
      "instIdList": ["BTC-USDT"]
    },
    "dateQuery": {
      "dateAggrType": "daily",
      "begin": "1704067200000",
      "end": "1704067200000"
    }
  }
  ```
* **Параметры:**
  * `module`: 
    * `"1"` — Trades (сделки)
    * `"2"` — Candlesticks (свечи)
    * `"3"` — Funding Rates (ставки финансирования)
    * `"4"` — L2 Order Book 400lv (стакан 400 уровней)
    * `"5"` — L2 Order Book 5000lv (глубокий стакан 5000 уровней)
  * `instType`: `"SPOT"`, `"SWAP"`, `"FUTURES"`, `"OPTION"`
  * `instQueryParam`:
    * Для SPOT: `{"instIdList": ["BTC-USDT"]}`
    * Для SWAP/FUTURES: `{"instFamilyList": ["BTC-USDT"]}` (указывается семейство)
  * `dateQuery`:
    * `dateAggrType`: `"daily"` или `"monthly"`
    * `begin` / `end`: Unix timestamp в миллисекундах (в виде строки).
* **Пример ответа (Response):**
  ```json
  {
    "code": "0",
    "data": {
      "details": [
        {
          "instId": "BTC-USDT",
          "instType": "SPOT",
          "groupDetails": [
            {
              "dateTs": "1704038400000",
              "filename": "BTC-USDT-trades-2024-01-01.zip",
              "sizeMB": "1.86",
              "url": "https://static.okx.com/cdn/okex/traderecords/trades/daily/20240101/BTC-USDT-trades-2024-01-01.zip?v=1000"
            }
          ]
        }
      ]
    },
    "msg": ""
  }
  ```
* **Лимиты (Rate Limit):** ~1–2 запроса в секунду. При частых вызовах возвращает `HTTP 429 Too Many Requests`.

### 2.3. Оперативный REST API v5 (для недавних данных)

1. **История сделок (до 3 месяцев назад):**
   * **URL:** `GET https://www.okx.com/api/v5/market/history-trades`
   * **Параметры:**
     * `instId` (обязательный): инструмент, например `BTC-USDT`
     * `limit`: количество записей (макс. 100)
     * `type`: `"1"` (пагинация по `tradeId`) или `"2"` (пагинация по `ts`)
     * `after`: указатель на более старые записи (`tradeId` или `ts`)
     * `before`: указатель на более новые записи (`tradeId` или `ts`)
   * **Rate Limit:** 10–20 запросов за 2 секунды.

2. **Текущий срез стакана L2:**
   * **URL:** `GET https://www.okx.com/api/v5/market/books`
   * **Параметры:**
     * `instId`: инструмент (`BTC-USDT`)
     * `sz`: глубина стакана (по умолчанию 1, максимум 400)
   * **Rate Limit:** 20 запросов за 2 секунды.

## 3. Формат получаемых данных и схема колонок

### 3.1. Сделки (Trades)
* **Файл:** CSV внутри ZIP-архива (`{instId}-trades-{YYYY-MM-DD}.csv`).
* **Разделитель:** Запятая `,`.
* **Кодировка:** `utf-8` / `ascii`.
* **Единицы времени:** Unix timestamp в **миллисекундах** (`created_time`).
* **Схема колонок:**

| № | Колонка | Тип данных | Описание | Пример |
|---|---|---|---|---|
| 1 | `instrument_name` | String | Тикер инструмента | `BTC-USDT` |
| 2 | `trade_id` | Int64 / String | Уникальный ID сделки биржи | `465953984` |
| 3 | `side` | String | Направление инициатора (`buy` или `sell`) | `buy` |
| 4 | `price` | Float / Decimal | Цена исполнения сделки | `42457.6` |
| 5 | `size` | Float / Decimal | Объем (в базовой валюте для Spot, в контрактах для Swap/Futures) | `0.00118219` |
| 6 | `created_time` | Int64 | Время совершения сделки (epoch ms, 13 цифр) | `1704038400149` |

**Пример сырых данных:**
```csv
instrument_name,trade_id,side,price,size,created_time
BTC-USDT,465953984,buy,42457.6,0.00118219,1704038400149
BTC-USDT,465953985,buy,42457.6,0.00604855,1704038400149
BTC-USDT,465953986,buy,42457.6,0.00515982,1704038400408
```

---

### 3.2. Глубокий стакан заявок L2 (Order Book 400lv)
* **Файл:** Текстовый файл `.data` внутри архива `.tar.gz`.
* **Формат данных:** **Newline-delimited JSON (NDJSON)** — каждая строка представляет собой самостоятельный валидный JSON-объект.
* **Единицы времени:** Unix timestamp в **миллисекундах** (`ts`).
* **Схема полей JSON:**

| Поле | Тип | Описание |
|---|---|---|
| `instId` | String | Идентификатор инструмента (`BTC-USDT`) |
| `action` | String | Тип события: `"snapshot"` (первичный слепок книги) или `"update"` (дифференциальное обновление) |
| `ts` | String (Int64) | Unix timestamp в миллисекундах |
| `asks` | List[List[str]] | Список ценовых уровней на продажу `[price, size, num_orders]` |
| `bids` | List[List[str]] | Список ценовых уровней на покупку `[price, size, num_orders]` |

#### Правила обновления книги заявок (L2 Order Book Logic):
1. **Начало файла:** В большинстве архивов первая строка имеет `action: "snapshot"` (базовый срез активных уровней на начало суток). Однако за некоторые даты (например, `2024-01-02`) файл может начинаться с серии дифференциальных обновлений `action: "update"`, а первый `snapshot` приходит позже (через несколько секунд или десятков секунд). В таких ситуациях книга считается неполной до первого снапшота: этап валидации ставит `WARN` (если снапшот пришел в пределах 120 с) или `FAIL` (если снапшота нет вовсе), а бэктест-движок начинает симуляцию строго после прихода первого полноценного `snapshot`, игнорируя предшествующие сделки.
2. **Последующие строки** имеют `action: "update"`:
   * Если уровень `[price, size, num_orders]` имеет `size > 0`: уровень обновляется или добавляется в стакан.
   * Если уровень имеет `size == "0.0"` или `num_orders == "0"`: данный ценовой уровень **удаляется** из стакана.

**Пример сырых данных:**
```json
{"instId":"BTC-USDT","action":"snapshot","ts":"1704067200018","asks":[["42284.0","0.81036","7"],["42284.2","1.072e-05","1"]],"bids":[["42283.9","0.99304163","5"],["42283.6","0.03448185","1"]]}
{"instId":"BTC-USDT","action":"update","ts":"1704067200028","asks":[],"bids":[["42276.1","0.00425767","1"],["42059.1","0.0","0"]]}
{"instId":"BTC-USDT","action":"update","ts":"1704067200038","asks":[["42284.0","0.58516","5"],["42293.4","1.007e-05","1"]],"bids":[["42276.1","0.0","0"],["42241.4","0.00429522","1"]]}
```

## 4. Инженерные нюансы для реализации в коде

### 1. Часовой пояс суточной партиции (UTC vs UTC+8)
* OKX нарезает суточные архивы по часовому поясу Гонконга (**UTC+8**, `Asia/Hong_Kong`).
* Это означает, что файл с датой `2024-01-01` содержит данные за интервал:
  * `2024-01-01 00:00:00 UTC+8` — `2024-01-01 23:59:59 UTC+8`
  * Что в UTC соответствует: `2023-12-31 16:00:00 UTC` — `2024-01-01 15:59:59 UTC`.
* **Что заложить в код нормализатора:** При фильтрации диапазона бэктеста нельзя отталкиваться от названия файла. Нужно строго парсить поле `created_time` / `ts` и производить фильтрацию по реальному времени события в UTC.

### 2. Задержка появления свежих архивов (Daily SLA)
* Архивы за вчерашний день появляются на CDN около **00:00:50 UTC** следующего дня (задержка меньше 1 минуты после завершения суток UTC).
* **Что заложить в планировщик:** Ночной `cron` для докачки данных за вчерашний день можно безопасно запускать в **00:15–00:30 UTC**.

### 3. Потоковая обработка тяжелых стаканов (Memory Management)
* Суточный файл книги заявок в распакованном виде занимает **от 1 до 4 ГБ**.
* **Что заложить в код:**
  * Ни в коем случае не читать файл целиком в оперативную память (`f.read()`).
  * Читать архив потоково чанками напрямую из потока распаковщика:
    ```python
    with tarfile.open(fileobj=stream, mode="r|gz") as tar:
        for member in tar:
            f = tar.extractfile(member)
            for line in f:  # построчная обработка NDJSON
                process_orderbook_event(line)
    ```

### 4. Двойной URL для Order Book (Fallback `/pro/`)
* В URL стаканов OKX изменил структуру папок: свежие даты содержат сегмент `/pro/`, а старые — нет.
* **Что заложить в код:** Метод генерации ссылки должен сначала проверять URL с `/pro/`, а при получении `HTTP 404` делать fallback на классический URL без `/pro/`.

### 5. Идемпотентность и стратегия скачивания
* Перед отправкой HTTP-запроса скрипт должен проверять наличие файла в `data/raw/trades/{symbol}-{date}.zip`. Если файл существует и валиден (проверка `zipfile.is_zipfile`), сетевой запрос пропускается.
* При 429/500/502/503 ошибках обязателен механизм **Exponential Backoff** (паузы 1s -> 2s -> 4s -> 8s).
